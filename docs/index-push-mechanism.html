Committed WAL to durable index progress

Each main-table bucket and index has one active IndexWindow. Every Index Bucket batch is admitted as one unit, and main-table WAL progress advances only after all Index Bucket batches are durably acknowledged.

Target ordering across different window boundaries

Writer progress is the exclusive end offset of a main-table WAL range. Old and new leaders may form different windows, while the Index Bucket keeps the greatest committed progress for each WriterKey.

Independent main-table and Index Table recovery

Main-table recovery requires committed indexPushedOffset and continuous raw WAL. Index Table recovery requires a KV snapshot, a complete cumulative-progress WriterState snapshot, and continuous Index Table WAL. A missing required range refuses leadership.

NO_SNAPSHOTWithout a main-table KV snapshot, replication starts at offset 0.
MISSING_PROGRESSA main-table snapshot missing indexPushedOffset refuses recovery instead of guessing logStartOffset.

Three consumers of partition tombstones

The Coordinator's floor plus explicit set is the sole authority. Write apply is not-ready before baseline initialization; query filtering and compaction are pruning paths, while client deduplication and recheck preserve read correctness.

BLACKLIST_MONOTONICA stale cache deletes less and never misclassifies an alive partition as deleted.
WRITE_NOT_READYAn internal write against UNINITIALIZED state is retryable and has no side effects.
QUERY_OPTIMIZATIONThe server filter reduces network and Hop 2 fanout but does not own final correctness.
PHYSICAL_RECLAIMCompaction physically removes a hit; index rows contain no logical-delete field.

Candidate convergence in Two-Hop lookup

Hop 1 returns physical candidates. The client deduplicates complete logical primary keys by content, performs one point get per key, and applies type-aware equality against the current row.

CONTENT_EQUALITYbyte[] and BinaryString values compare by content, never by object identity.
PER_CALL_STATEThe dedup set, futures, and expected values are not shared across lookup calls.
FALSE_POSITIVE_GUARDRecheck removes stale pointers without claiming MVCC snapshot completeness.
WARN_NOT_LIMIT1024 triggers only a low-selectivity warning; it neither truncates candidates nor caps Hop 2.

Index storage and idempotence formats

Index Tables explicitly select cumulative progress mode. Ordinary KV tables keep contiguous batch sequences, while Log Tables and ProduceLog do not use this KV setting. An Index Table created for a partitioned main table remains non-partitioned, but adds physical partitionId isolation and the v3 value tag.

TABLE_BOUND_MODEA missing property selects contiguous batch sequences; system-derived Index Tables explicitly set value 1.
API_IS_TRANSPORTPutKv API v2 transports cumulative-progress batches and never selects or downgrades the table mode.
SHORT_VALUE_GUARDJava and native filters require at least 10 bytes before reading the 8-byte tag.
NO_FORMAT_DOWNGRADEOnce cumulative-progress state exists, binaries that cannot read its formats cannot be used.
